## Regression (full automated run)

- Frontend: `cd frontend && npm run lint` → clean (tsc --noEmit, no errors).
  `cd frontend && npm test` → **238 test files, 2638 tests, all passing** (vitest, ~20s).
  This is the entire existing frontend test suite, run unmodified, after every change in this
  branch — the strongest evidence available tonight that nothing else broke.
- Backend: `cd backend && npm run lint` → clean (tsc --noEmit, no errors). `npm test` (real
  `node --test` against a real MySQL instance) was **not run** — no MySQL instance was started
  or connected to tonight, consistent with the hard gate against touching a live/shared
  database; the only backend change is one settings-definition entry plus one small, fully
  isolated module (`src/templates/`) with no DB access of its own.

## Known gaps (honestly NOT claimed as PASS)

1. **No E2E / live-flag verification.** Everything above was verified with the flag's
   *default* (off) state, static code reading, or pure-function unit tests. Nobody has ever
   actually seen these sample buttons render and work end-to-end in a running browser with the
   flag turned on — that requires a running dev server + (for the full backend-backed flag
   check) a real `app_settings` row, which this pass deliberately did not stand up. **Before
   enabling the flag in any shared environment, run the existing `scripts/doc-tools/check-*.mjs`
   / `check-a11y.mjs` Playwright scripts against a dev server with the flag on.**
2. **T13 (OCR) and the "real compare engine" half of T16** need a live browser (DOM/canvas,
   Tesseract WASM) and were not run.
3. **T24 (mobile/a11y) and T29 (performance)** need the project's own Playwright/Lighthouse-style
   scripts against a running app and were not run.
4. **.docx fidelity (T04/T09)** is weaker than .xlsx/.pdf: only zip-validity was asserted, not a
   full re-parse of headings/paragraphs/table cells (no lightweight pure-JS .docx reader was
   readily available to add tonight without pulling in a new dependency).
